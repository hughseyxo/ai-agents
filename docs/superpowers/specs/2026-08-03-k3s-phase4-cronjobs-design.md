# Phase 4 — CronJobs Cutover Design

## Related

Sub-project of [[2026-08-01-k3s-migration-design]] (Phase 4 bullet). Follows [[2026-08-03-k3s-phase3-wedding-ui-cutover]] (Phase 3, done — first real workload on the cluster, established the manifest/imagePullSecret/rollback-drill patterns this phase reuses).

## Problem

The 6 agent classes in `agents/` (`agent-health`, `plant-agent`, `daily-briefing`, `news-briefing`, `security-audit`, `librarian`) currently run via the host's crontab. `agent_health.py`'s own schedule comment calls it "hourly — deterministic, no LLM" — the lowest-risk, easiest-to-verify agent in the fleet (no external API calls, no LLM synthesis, just reads local SQLite and checks staleness). It's the natural first agent to prove the CronJob pattern on, before the design doc's later phases (5–8) build on it for higher-stakes workloads.

## Scope

This phase creates K8s `CronJob` manifests for **all 7 cron-triggered resources** (6 agent classes; `librarian` contributes 2 — `--mode audit` and `--mode watch`, per its own `cron_entries()`), but only cuts `agent-health` over for real. The other six stay `suspend: true` and inert; their agents keep running via the host's existing crontab, completely untouched by this phase. Creating all 7 now (rather than just `agent-health`'s) means the shared infrastructure — image, namespace, secrets pattern, initContainer, hostPath mounts — is proven once, and later phases only need to flip `suspend: false` on their own CronJob plus do their own cutover/rollback drill, not invent the pattern from scratch.

## Architecture

- **Image:** reuses the existing `ai-agents-runner` image (`Dockerfile.runner`, built and pushed by CI since Phase 1). No new image needed. Container `command` per CronJob: `python3 -m agents <name>` (or `<name> --mode <mode>` for librarian), matching the host's `run-agent.sh` invocation exactly.
- **Namespace:** a new `ai-agents-cron` namespace, PSA `privileged` — **not** a reuse of the existing `ai-agents` namespace (Phase 2, PSA `baseline`) as originally planned. Discovered during implementation (a `kind` smoke test caught it before the real cluster did): Kubernetes' `baseline` PSA profile forbids `hostPath` volumes outright — only `privileged` allows them — so `agent-health`'s hostPath-mounted `data/agents.db` and OAuth token files could never have actually run in `ai-agents`. Scoping the looser PSA to a namespace dedicated to just these 7 CronJobs (rather than loosening `ai-agents` itself) keeps the blast radius narrow, matching the existing pattern of `wedding-ui` having its own namespace with its own PSA level. A new `default-deny-egress` `NetworkPolicy` (DNS + outbound TCP/443, identical shape to the existing `ai-agents` one) is added for `ai-agents-cron` too, since namespace-scoped policies don't carry over.
- **`imagePullSecret`:** a fresh PAT-backed `kubernetes.io/dockerconfigjson` Secret in the `ai-agents` namespace, same pattern as Phase 3's `ghcr-pull-secret` (scoped `read:packages`, generated by the human partner via the terminal `!` prefix so the PAT never enters the assistant's context).

## Shared state: hostPath, not PVC

Both `data/agents.db` (SQLite — dedup, run history, `agent-health`'s staleness reads) and `~/.google_tokens.json` (OAuth refresh token, rewritten on every refresh) are **hostPath-mounted** into every CronJob pod, pointing at the exact files the host-cron agents still read/write during this phase's transition period.

**Why not a PVC with its own copy:** the other six agents keep running on the host throughout this phase. A separate copy would let `agent-health`'s staleness checks silently diverge from reality (defeating the point of moving it first), and — more seriously — Google's refresh-token rotation can invalidate a sibling copy's token when two independent processes refresh independently. hostPath keeps a single source of truth and ties these pods to the one k3s node, which is an accepted tradeoff already made for `wedding-ui`'s `local-path` PVC (this is a single-node cluster).

## Secrets: scoped per agent, not the whole `.env`

A K8s `Secret` (or a small number of them, grouped by overlap) carries only the environment variables each agent actually needs — not the entire `.env` file. `agent-health` needs essentially nothing beyond what the `check-google-token.sh` initContainer requires generically (`GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET`); agents further down the line (not live this phase, but their Secrets get created too so their manifests are complete and valid) need whatever their own `.env` usage requires. The implementation plan enumerates the exact per-agent variable list by reading each agent's actual code path (including what the `claude`/`agy` CLI and MCP servers it invokes read from the environment) — this is execution-level legwork, not a further design decision; the decision made here is least-privilege scoping over a blanket hostPath/Secret mount of the whole `.env`.

## CronJob spec mechanics

- **No `timeZone:` field** — every `cron_entries()` schedule in `agents/` is already expressed in UTC (matches the existing host crontab convention noted in `CLAUDE.md`).
- **`concurrencyPolicy: Forbid`** — a slow run must never overlap the next scheduled tick.
- **`backoffLimit: 0`** — no Job-level retries. A failed run waits for the next tick, matching `BaseAgent`'s existing `partial_failure`-not-retry philosophy (retries are handled inside a run's own step logic, not by re-running the whole Job).
- **`activeDeadlineSeconds`**, set per-agent, well under that agent's own schedule interval:
  - `agent-health`: near-immediate (deterministic, no LLM call — seconds to low minutes). A short deadline (e.g. 300s) is generous headroom.
  - LLM-calling agents on tighter schedules (e.g. hourly `plant-agent`): needs enough headroom under `synthesize()`'s ~60 min worst-case timeout without eating into the next hourly tick. The design doc's own concern (Phase 4 bullet) is exactly this: an unbounded worst case would otherwise swallow the next hourly run. The implementation plan computes an exact value per agent's own interval (roughly: interval minus a safety margin, capped below the 60 min LLM timeout for hourly agents).
- **`check-google-token.sh` as an `initContainer`**, wired up on **all 7** CronJob pods uniformly — matches `run-agent.sh`'s existing unconditional behavior on the host (it sources the check before *every* agent run, not just Google-API-using ones), so this phase replicates existing behavior rather than inventing new conditional logic.
- **Per-agent `--strict-mcp-config` isolation** (e.g. `news-briefing` reaching zero MCP servers) is **already enforced** by existing Python logic in `agents/base.py` (`mcp_config = None` default, `_tool_restriction_flags()`). This phase adds no new isolation mechanism — the container's `python3 -m agents <name>` invocation exercises the identical code path the host does, by construction. Verification is confirming this, not building it.

## Cutover procedure (agent-health only)

1. Apply all 7 CronJob manifests to the real cluster with only `agent-health`'s `suspend: false`. Watch its next scheduled hourly run fire from k8s, confirm it reads/writes the shared hostPath `data/agents.db` correctly and reports success identically to a host-cron run.
2. **Bake time:** verify **3 consecutive successful in-cluster hourly runs** (a few hours, not the full week the parent design doc's Verification section describes generically for "a week of `agent-health` cluster-only runs" — this is a homelab, not a production system, and a shorter soak still catches flakiness without holding the phase open unnecessarily long). Once 3 clean runs are confirmed, remove `agent-health`'s line from the host crontab — the actual cutover.
3. **Rollback drill, actually executed** (matching every prior phase's bar, not just documented): re-add `agent-health`'s host crontab line, `suspend: true` its k8s CronJob, verify the host resumes running it on its next tick, then re-cut-over (remove the crontab line again, `suspend: false` the CronJob) to leave the phase in its intended end state.

## Verification

- All 7 CronJob manifests pass `kubeconform --ignore-missing-schemas` in CI (same gate as every other `k8s/base` addition).
- `agent-health`'s in-cluster runs write identical-shaped rows to `data/agents.db` as its prior host-cron runs did (spot-check via SQLite query before/after cutover).
- The other six CronJobs remain `suspend: true` and never fire during this phase — confirmed via `kubectl get cronjobs -n ai-agents` showing no `LAST SCHEDULE` activity on them.
- Rollback drill (Step 3 above) actually executed, both directions.
- Existing `pytest tests/` suite stays green throughout (no agent Python logic changes in this phase — it's manifests + host crontab only).
