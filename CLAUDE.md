# Token Efficiency Rules
- **Be terse.** Short answers, no filler, no restating what I said.
- **Don't explore what's documented here.** For project structure, read the server-only map (`docs/_map/index.md` → per-area notes) on demand — don't glob/grep to rediscover it.
- **Don't read skill files unless editing them.** The summaries below are enough for context.
- **Don't read MCP server source unless debugging them.** Tool names are discoverable via MCP; the code is auth/plumbing.
- **Skip preamble.** No "Let me...", "I'll now...", "Great question!" — just do the thing.
- **One-shot edits.** Read a file once, make all changes, move on. Don't re-read to verify unless the edit is high-risk.
- **Minimise subagent use.** Only spawn agents for genuinely parallel or deep-search tasks. Direct tool calls are cheaper.

# Agent Conventions
- Agents are Python classes in `agents/` extending `BaseAgent`
- **Dual-CLI rule:** All agent Python code must be runnable by both Claude and Antigravity CLI. No Claude-specific or Antigravity-specific dependencies in Python. LLM-specific adaptations happen in `BaseAgent.synthesize()` only.
- Execution model: Python handles lifecycle, state (SQLite), retry, dedup, and deterministic logic (e.g. plant watering, weather, RSS fetching). LLM CLI (with MCP tools) handles data synthesis and formatting. **Email is sent directly via `agents/gmail_client.py`** (no LLM/MCP transport) — the LLM is reserved for content synthesis (translation, scoring, status text), not sending.
- **Model selection:** Set `model = "claude-sonnet-4-6"` (or haiku/opus) on the agent class. `BaseAgent.synthesize()` maps these to appropriate Antigravity models when using Antigravity, or passes them directly to Claude.
- **Per-agent provider override:** Set `providers = [...]` on the agent class to change provider order. Default is Antigravity-first; `news_briefing` overrides to Claude-first. See `BaseAgent.PROVIDERS` for the full list.
- **LLM failover & Timeouts:** `BaseAgent.synthesize()` tries providers in order, adapting prompts for Antigravity at runtime.
  - **Timeouts:** A 600s timeout is applied to LLM calls. If a step marked with `side_effects: True` times out, the agent skips retries to avoid duplicate actions (e.g. sending multiple emails).
- **On-demand agents:** Set `schedule = ""` — they won't appear in crontab but can be triggered manually or via Telegram bot. Pass extra args via `configure(args)` called by `cmd_run` in runner.py.
- **LLM tool surface (security-critical):** `synthesize()` runs the claude CLI with `--dangerously-skip-permissions`, and agent prompts embed external content (RSS, web pages, calendar/email text). Two class attributes confine it — see `BaseAgent._tool_restriction_flags()`:
  - `mcp_config` — path relative to REPO_ROOT. **Default `None` means `--strict-mcp-config` with no config, i.e. zero MCP servers.** Only `daily-briefing`, `librarian` and `travel-agent` set it (`.mcp.json`); everything else reaches no MCP tools at all.
  - `allowed_tools` — tools re-enabled on top of the read-only defaults; anything listed is removed from the module-level `DENIED_TOOLS`.
  - **`--allowedTools` does NOT restrict** — verified against the real CLI: allowlisting only `gmail_send` still exposed every Gmail tool. **`--disallowedTools` is the only mechanism that enforces**, so new capabilities must be added to `DENIED_TOOLS`, not merely left off `allowed_tools`.
  - **MCP tools are deferred behind `ToolSearch`**, so agents needing MCP must list `ToolSearch` in `allowed_tools` or they silently never send. `ToolSearch` is denied by default because it also unlocks `CronCreate`/`SendMessage`/`RemoteTrigger` — persistence and egress without ever touching Bash.
  - `news-briefing` (`untrusted_input = True`) deliberately gets **no MCP and no tools**: it only translates/scores, and its email is built and sent in Python by `_send_report()`.
  - Residual by design: `Read`/`Glob`/`Grep` remain, so an injection can read repo files; output only reaches your own inbox. `agy` has no equivalent flags, which is why `untrusted_input` excludes it entirely.

# Security & Git Workflow
- **Security Audit Before Push:** Antigravity MUST run the security audit agent (`run-agent.sh security-audit`) before every `git push` to a public branch. If any "Critical" or "High" severity findings are found in unpushed or staged changes (Check 16), the push MUST be aborted until fixed or explicitly exempted by the user.
- **Atomic Commits:** Prefer small, focused commits with clear descriptions.
- **No Secrets:** Never commit `.env`, `credentials.json`, or any files containing API keys or private data.
- **Media Files:** Do not commit `.mp4`, `.mkv`, or other large media files downloaded by agents.

- Run via: `run-agent.sh <agent-name>` or `python3 -m agents <agent-name>`
- Each agent declares its own cron schedule via `cron_entries()`; `python3 -m agents install-cron` writes ALL crontab entries from every agent's `cron_entries()` (including librarian's non-default `--mode` entries) into the managed block — it is the single source of truth for crontab, not a partial list
- Agent state lives in `data/agents.db` (SQLite) — never store secrets there
- MCP servers (Todoist, Calendar, Gmail) are used via LLM CLI (Claude or Antigravity), not called directly from Python. Both CLIs have identical MCP server configs — Claude via `.mcp.json`, Antigravity via `~/.antigravity/antigravity-cli/mcp_config.json`.
- Step failure handling: if a step exhausts retries, execution continues but the run is marked `partial_failure` in the DB (not `success`). Check `_failed_steps` in `report()` if you need to adjust output.
- Agents log operational notes (feed failures, API quirks, unexpected behavior) to `docs/agent-notes.md` (gitignored) to save tokens on future runs
- All cron schedules target 6:00 AM Amsterdam time (CEST = UTC+2, so 04:00 UTC)

# Plant Watering Tracker
- Data lives in `data/agents.db`, row-per-plant in the dedicated `plants` table, managed by `PlantStore` (`agents/plant_model.py`) — tools, agents, and the daily briefing all read/write through it. The old single-blob state key (`agent="daily-briefing", key="plants"`) is migrated lazily on first read and left in place as a legacy/rollback copy only; it is NOT kept in sync after migration, so nothing should read/write it directly outside `PlantStore`. CLI tool is `plant.sh` (add/list/remove/--outdoor)
- Plant data model: `{name, baseline_frequency_days, frequency_days, last_watered, location, sunlight, water_sensitivity}` — `baseline_frequency_days` is the intrinsic cadence (changed by intelligence runs and the concierge `set_plant_frequency` tool); `frequency_days` is the **effective** value recomputed hourly = clamp(baseline + weather delta, 1, 30), folding indoor/outdoor + shade tolerance (so it's derived — don't hand-edit it). Migrated automatically (baseline defaults to frequency_days on first run). location is `"indoor"` or `"outdoor"`; water_sensitivity is `"high"/"medium"/"low"` (auto-researched via Antigravity at add time, defaults to `"medium"`)
- **Master agent:** `PlantAgent` (hourly) owns the plant lifecycle — weather cache refresh, status email, and intelligence runs. Replaces the old `PlantWeatherAgent`. (Todoist sync, task creation, and photo requests were removed — the FloraPulse PWA is now the task source of truth.)
  - Weather cache written to `plant_weather_cache` table; `get_plant_status()` in the concierge bot reads from it
  - Indoor: ±1-2 days adjustment based on temp/humidity; Outdoor: ±1-3 days based on rain/heatwaves
  - Weather fetch failure is non-fatal — cache not updated, bot falls back to base schedule
  - `agents/weather.py`: Open-Meteo is primary, wttr.in is an automatic fallback (Open-Meteo had a ~24h 502/503 outage on 2026-07-08/09). Both return the same dict shape; wttr.in approximates `recent_precip_mm` with the current hour's reading only (no past-24h endpoint on its free tier).
- **Plant profiles:** `docs/plants/<slug>.md` — created automatically, updated by intelligence runs. Contain observed behaviour, health assessments, frequency history, LLM notes, and a `## Linked Notes` section listing observation notes created for that plant.
- **Garden observation notes:** `docs/plant-observations/<slug>/YYYY-MM-DD-<title>.md` — auto-created on noteworthy photo assessments (both Telegram bot and PWA photo paths) and via concierge MCP tools. Linked from plant profiles' `## Linked Notes`.
- **Garden knowledge notes:** `docs/garden-knowledge/<topic>.md` — general gardening knowledge captured via concierge tools or chat. Not plant-specific.
- Both new note directories sync to CouchDB ~30s (same livesync-bridge as the rest of `docs/`).
- **When adding a plant without an explicit frequency:** search the web for recommended indoor watering cadence, check at least 3 sources, and use the consensus value. Do NOT default to 7 days.
- **Garden digest → Claude.ai Project sync (one-way):** `agents/plant_digest.py` (`build_digest()`) assembles a single consolidated "Plant Health Digest" Markdown doc (summary table + per-plant section combining core fields, weather-adjusted next-water date, and `read_profile_context()`). `PlantAgent._push_digest` (`agents/plant_agent.py`) pushes it to Google Drive at the end of each intelligence run (~daily) via `agents/drive_client.py`, so a Claude.ai Project on mobile/web with that Drive folder linked as knowledge always has current garden data. Push is best-effort — a Drive failure is logged to stderr and never blocks the intelligence run.
  - **Drive OAuth is separate from Gmail/Calendar:** `agents/drive_client.py` uses its own token file (`~/.google_tokens_drive.json`, `drive.file` scope) rather than the shared `~/.google_tokens.json`, so a Drive re-consent can never disturb the working Gmail/Calendar tokens. Same OAuth client (`GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET` in `.env`) as Gmail/Calendar, just a different scope grant. One-time setup: `python3 scripts/setup_drive_oauth.py`.
  - **Manual, one-time, outside this repo:** in the Claude.ai Project (mobile or web), add Google Drive as a knowledge source and select the "Plant Health Digest" folder. This cannot be automated — Claude.ai's consumer Project knowledge base has no API for pushing files directly.

- **Batch photo upload:** dashboard "Batch Upload" FAB → `POST /api/plants/batch-photos` (multi-file) creates a job processed by `agents/photo_batch.py` (`asyncio.create_task`, off the event loop via `asyncio.to_thread` — the underlying `claude` CLI calls are blocking subprocesses). On a hit, the job pauses, persists state, and pings every 5 min (`PING_INTERVAL_SECONDS`) up to a 2h cap (`MAX_PAUSE_SECONDS`) before giving up (`status=failed`). Job state (`photo_batch_jobs` table) and a job-scoped temp dir (`data/plant-photo-batches/<job_id>/`) persist across a `plant_ui` service restart — resumed automatically via the FastAPI `lifespan` startup hook (`photo_batch.resume_active_jobs()`).

Neither `data/plant-photos/` nor `data/plant-photo-batches/` sync to Obsidian (outside `docs/`).
  - **Toast component:** `.toast-container`/`.toast` in `style.css` + `showToast()`/`toasts[]` in `app.js` — scoped to batch/manual-assign feedback only; every other action still uses `alert()`/`confirm()` (not a full migration).

- **Auth: in-app passcode login, NOT Traefik basic auth.** `grabau_ui/auth.py` + `/login` serve a shared-passcode form and set an HMAC-signed HttpOnly session cookie (`grabau_session`, 1 year). **Basic auth was removed because it is unusable on iOS**: in-app browsers (WhatsApp/Instagram/Mail webviews) and installed Home Screen PWAs never render the credentials prompt — they just show Traefik's bare `401 Unauthorized`, so a link shared in a chat app looks broken. Don't "restore" basic auth here.
  - Passcode + cookie key come from `GRABAU_PASSCODE` / `GRABAU_SECRET`, set in the seedbox's gitignored `.env.custom` as `ITALY-WEDDING_GRABAU_*` (run-seedbox strips the `ITALY-WEDDING_` prefix into `env/italy-wedding.env`).
  - **Fails closed:** no `GRABAU_PASSCODE` → every non-public path returns 503. Public paths: `/login`, `/logout`, `/healthz`, `/sw.js`, `/static/*`, `/metrics`.
  - Brute-force throttle: 10 failed attempts per client IP (via `CF-Connecting-IP`) per 15 min → 429.
  - `config.yaml` still sets `traefik.enabled: false` and the router lives in `samples/custom-traefik/italy-wedding.yaml` (copied to `traefik/custom/custom-*.yaml` on each run), because the seedbox's `httpAuth: true` flag can only attach `common-auth@file` — whose users file grants access to *every* protected service on the domain.
- **Traefik gotcha (middleware order):** `redirect-to-https` must come BEFORE the auth middleware. Auth-first challenges bare-hostname visitors for credentials over plaintext HTTP — browsers suppress that prompt, then re-prompt after the HTTPS redirect, so the link looks broken. `run-seedbox.sh` generates the opposite order for every `httpAuth: true` service (wedding, plant, mealie, portainer…) — pre-existing, unfixed.
- **Traefik gotcha (templating):** dynamic files are Go-templated — `{{ env "TRAEFIK_DOMAIN" }}` must be in a **single-quoted** YAML scalar. Escaped double quotes break the whole file (`template: unexpected "\\" in operand`) and Cloudflare then serves **525** because no cert is requested.
- **Deploy gotcha (bit me once, briefly served the app unauthenticated):** `./run-seedbox.sh` does NOT rebuild an image that already exists — it recreates the container from the stale image. After changing any `grabau_ui/`/`wedding_ui/`/`plant_ui/` source you MUST rebuild first:
  `cd ~/git/ai-agents && docker build -f grabau_ui/Dockerfile -t grabau-fund:latest . && cd ~/git/yopflix/seedbox && ./run-seedbox.sh`
- **`Form(...)` needs `python-multipart`** in `requirements.txt` — it's in the repo venv, so tests pass while the container crash-loops on startup without it.
- **Seedbox files** (in the separate `~/git/yopflix/seedbox` repo): `services/italy-wedding.yaml`, `samples/custom-traefik/italy-wedding.yaml`, `config.yaml` entry, `.env.custom` (`ITALY-WEDDING_GRABAU_*`). No `http_auth_italy` any more — deleted with basic auth.
- **Verification:** `.venv/bin/pytest tests/test_grabau_ui_api.py` (31 tests, incl. the auth gate). Design doc: `docs/superpowers/specs/2026-08-29-villa-grabau-wedding-pwa-design.md`.

# Job Hunt (LinkedIn matches + application tracker)
- **Role:** Daily `job-hunt` agent (`agents/job_hunt.py`, cron 04:00 UTC) + Tailscale-only `jobs_ui/` PWA. Replaces the unshipped fintech/pharma `job-alert` agent (deleted, along with its daily-briefing section).
- **No hard-coded roles/sectors:** when the CV changes, an LLM call derives 6–10 LinkedIn queries from it (no location words, no near-duplicates) (validated: ≤40 chars, `[\w .+/#-]`). Manual queries can be added in the UI. The CV-fit score (0–100) does the filtering. Search: NL, `f_WT` remote(2)+hybrid(3), last 48h, via `agents/linkedin_jobs.py` (public guest API, unofficial; ~5–8s jittered spacing, one 60s back-off on 429, a second 429 aborts the step and saves a `fetch_cursor` in agent state so the next run starts at the query that was cut off).
- **Steps:** `cv` → `fetch` → `triage` (Haiku, title only, drops only clear misfits) → `score` (Sonnet, ≤40/run, description from guest `jobPosting/{id}`) → `gmail` → `notify` (Telegram once per job with score ≥75, `parse_mode=None`).
- **CV:** newest owned `Cian_Hughes_CV_General*` Google Doc/.docx, fetched by `agents/drive_reader.py` through the **claude.ai Google Drive connector** in a headless `claude -p` (Haiku). No Google OAuth client or token: a custom `drive.readonly` OAuth app was blocked by Google. Confined with `--allowedTools ToolSearch` plus the two Drive read tools, and no `--dangerously-skip-permissions`, so anything else is auto-denied. Python parses the stream-json output and takes metadata/text from the raw tool results, verifying the newest CV was read. A hash change re-derives queries and re-scores open jobs from the last 14 days. If the fetch fails, the last stored snapshot is used.
- **Gmail (runs before the fetch):** `gmail_client.search_messages/get_message/extract_message` on the existing `gmail.modify` token. The window reaches back to the last fully drained sync (`gmail_last_ok` state + 2 days, clamped 7–90; 90 on first run). It processes ≤150 oldest-first per run and carries the backlog over, with dedup via `gmail_seen`. Haiku classifies each message as applied/interview/rejected/offer/other; the company must literally appear in the email or it's ignored. `JobStore.record_email_event` find-or-creates the application and never downgrades status. **Already applied/rejected:** `JobStore.reconcile_applications()` links jobs to applications (normalised company + seniority-insensitive role-token match, `SRE`→site reliability engineer, dismissed jobs skipped). Linked jobs get `status=applied` and `application_id`, drop out of triage/scoring/pings, and the UI shows 'Applied · rejected'. One application per job (unique index).
- **Security:** `untrusted_input=True`, no MCP, no `allowed_tools`, Claude-only providers. Every LLM field is re-validated in Python. UI renders with `x-text` only.
- **Data:** `data/jobs/jobs.db` (gitignored, own dir so the container mounts only it; WAL). `JobStore` (`agents/job_store.py`) is shared by the agent and the UI.
- **Hosting:** Docker image `jobs-ui:latest` (`jobs_ui/Dockerfile`, `APP_UID=1001` to match the host owner of the bind mount), container `jobs-ui`, bound to `<TAILSCALE_IP>:8774`, no Traefik, no login. Seedbox files: `services/jobs-ui.yaml` + `config.yaml` entry. Rebuild before deploying: `docker build -f jobs_ui/Dockerfile -t jobs-ui:latest .`
- **Dry run:** `python3 -m agents run job-hunt --dry-run`: no Telegram, no Gmail writes, report to `output/job-hunt-dry-run-<date>.md`.
- **Verification:** `.venv/bin/pytest tests/test_linkedin_jobs.py tests/test_job_store.py tests/test_drive_reader.py tests/test_gmail_search.py tests/test_job_hunt.py tests/test_jobs_ui_api.py`. Design: `docs/superpowers/specs/2026-10-15-job-hunt-design.md`; plan: `docs/superpowers/plans/2026-10-15-job-hunt.md`.
